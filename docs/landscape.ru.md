# Аналоги и позиционирование iupac2smiles

Проверка источников: 29 октября 2026 года. Это обзор возможностей, **не результаты
экспериментального сравнения** на общем тестовом наборе.

## Что уже существует

| Решение | Подход | Сильная сторона | Ограничение относительно нашего сценария |
| --- | --- | --- | --- |
| [OPSIN](https://www.ebi.ac.uk/opsin/) | Грамматика систематических названий, локальный Java CLI и web API | Офлайн-парсинг новых систематических имён; высокая точность в поддерживаемом пространстве | Не любой синоним или нестандартное название распознаётся |
| [IUPAC2Struct](https://github.com/sergsb/IUPAC2Struct) | Transformer name-to-structure | Модель конвертации химических названий | Возможны ошибочные структуры, нужен независимый тест |
| [chemical-converters](https://github.com/Knowledgator/chemical-converters) | Нейросетевые SMILES↔IUPAC модели | Готовый Python API для предсказаний | В описании модели отмечено отсутствие поддержки изомерных/изотопных SMILES; генерация не гарантирует правильность |
| [PubChem PUG REST](https://pubchem.ncbi.nlm.nih.gov/docs/pug-rest) | Поиск по названиям и синонимам в базе | Известные соединения и альтернативные названия | Не парсер произвольных новых имён; сетевой сервис |
| [NCI Chemical Identifier Resolver](https://cactus.nci.nih.gov/chemical/structure_documentation) | Поиск соответствий идентификаторов/имён | Много синонимов | Авторы отмечают проблемы с передачей стереохимии |
| [MoleculeResolver](https://github.com/MoleculeResolver/molecule-resolver) | Агрегация OPSIN, PubChem, CompTox и др.; crosscheck | Согласование результатов и воспроизводимый выбор структуры | Другая задача: разрешение идентификаторов по источникам, а не локальный нейронный fallback |
| [cholla_chem](https://github.com/denovochem/cholla_chem) | Агрегация резолверов и специализированные эвристики | Широкий охват реальных химических названий | Уже решает многие задачи, ради которых можно ошибочно добавлять новые провайдеры сюда |
| [ORD resolve_name](https://docs.open-reaction-database.org/en/latest/guides/compound_identifiers.html) | OPSIN и PubChem API | Простое разрешение имён в реакционных наборах | Внешние сервисы; требуется проверка корректности |

Особенно важна публикация Müller (2025), *How to crack a SMILES: automatic
crosschecked chemical structure resolution across multiple services using
MoleculeResolver*, DOI:
[10.1186/s13321-025-01064-7](https://doi.org/10.1186/s13321-025-01064-7).
Она показывает ценность перекрёстной проверки вместо доверия единственному
источнику. Кроме того, в работе *ReactionSeek* (Nature Communications, 2026)
названия приводятся к SMILES с помощью гибридной схемы
(базы/парсеры/LLM-assisted matching), а не свободной генерации без проверки:
[статья](https://www.nature.com/articles/s41467-026-70180-1).

## Направления конвертации: уточнение

**cholla_chem** реализует именно name → SMILES: публичный API
`resolve_compounds_to_smiles` и интерфейсы резолверов описывают преобразование
имён в структуры, а не создание систематических названий по SMILES.

**MoleculeResolver** также в первую очередь осуществляет name/CAS → structure,
но поддерживает обратный поиск идентификаторов: получение *существующих*
названий и CAS из баз по SMILES, InChI или InChIKey. Это не генератор новых
номенклатурных имён.

**STOUT / STOUT V2** — иной класс: нейросетевая генерация IUPAC по SMILES,
а в описании кода заявлена и обратная конвертация IUPAC → SMILES. Статья о
V2 опубликована 27 декабря 2024 года:
https://doi.org/10.1186/s13321-024-00941-x .
Авторы сообщают о публикации кода и весов как открытых ресурсов, а
предпечатка указывает лицензию MIT и архив моделей. Исходный GitHub
https://github.com/Kohulan/Smiles-TO-iUpac-Translator при проверке
29.10.2026 не открылся (404); исходники архивной версии доступны
в https://zenodo.org/records/14638076 , а публичная копия документации
по двум направлениям — https://github.com/egonw/Smiles-TO-iUpac-Translator .
**Статус актуальной рабочей установки с весами ещё не подтверждён.**
Не путать открытый код и веса STOUT с коммерческим Lexichem, использованным
для формирования обучающих названий.

STOUT — обязательный кандидат на сравнение по обратному направлению;
добавлять его в конвертер без измеримого преимущества не следует.

## Где может быть ценность iupac2smiles

Узкое позиционирование: **локальный, пакетный и воспроизводимый каскад
«OPSIN → нейросетевые модели» с прозрачным происхождением результата и честным
отказом при сомнительном предсказании**.

Не позиционировать его как универсальный резолвер всех химических идентификаторов
или как более точный инструмент, пока это не подтверждено на независимом benchmark.
RDKit-парсинг предсказанного SMILES проверяет валидность структуры, **не**
соответствие названия структуре.

## Критерии решения о дальнейшем развитии

1. Прогонять идентичные тестовые наборы через OPSIN, каждую ML-модель и каскад.
2. Считать **exact molecular match** по RDKit с учётом стереохимии, валидность,
   долю распознанных, точность среди распознанных, время и вклад каждого fallback.
3. Отдельно тестировать названия, которые OPSIN не смог преобразовать; без этого
   дополнительное покрытие ML-моделей легко переоценить.
4. Использовать как минимум один независимый внешний набор с известным
   происхождением: совпадения с обучающими данными и перекрытия между
   синонимами не допускают безоговорочной оценки обобщающей способности.
5. Если прирост правильно распознанных названий низок или достигается ценой
   существенных ложных структур, оставить OPSIN-only инструмент и
   прекратить расширять каскад.

**Что не добавлять без доказанной потребности:** ещё один нейронный backend,
копию MoleculeResolver, собственную химическую стандартизацию, веб-интерфейс,
LLM-агента.

## Запуск первичного benchmark

Опубликованный формат IUPAC2Struct содержит две колонки
«input, target»: reference SMILES, затем IUPAC name, разделитель — запятая и пробел.

~~~bash
pip install -e ".[ml,bench]"
curl -LO https://raw.githubusercontent.com/sergsb/IUPAC2Struct/main/data/smiles_lens_1000/80.csv
python scripts/benchmark.py 80.csv --backends opsin --json opsin-baseline.json
python scripts/benchmark.py 80.csv --json full-cascade.json
~~~

Первый файл измеряет baseline без ML. Второй загружает модели и может требовать
значительных ресурсов. Это **воспроизводимый сценарий**, а не утверждение,
что модели уже были протестированы в текущем PR.
